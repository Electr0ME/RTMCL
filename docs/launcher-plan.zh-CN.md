# RTMCL - Rust TUI Minecraft Launcher 启动器规划

- 日期：2026-10-20（Asia/Hong_Kong）
- 状态：P0 安装与启动基础设施已实现；曾用开发测试账户在 Windows / WSLg 验证主菜单，该测试登录现已按用户要求移除。当前只保留微软账户并强制在线认证，Minecraft Services 403 与完整正版会话仍待接入验收；严格镜像完整冷启动等证据仍待补齐。WSL / WSLg 验收暂缓。本文件中的功能目标不代表已实现，当前进度见 [工程边界](architecture.zh-CN.md) 与 [P0 验证记录](p0-validation.zh-CN.md)。
- 目标平台：Windows x64、Linux x64（GNU/glibc）；当前以 Windows 验收为主，WSL / WSLg 验收暂缓，保留 Linux 实现及历史证据。
- 启动器核心：LightyLauncherLib。
- 产品与工程参考：rmcl 的实例管理、终端交互、Java 探测、日志与测试组织。
- 首版硬性要求：原版、Fabric、微软登录、多实例、BMCLAPI 镜像与官方回退。

## 1. 目标与范围

实现轻量、键盘优先的 Minecraft Java 版启动器，形成“登录 → 创建实例 → 安装 → 启动 → 查看日志”的完整流程。提供 TUI 和基础 CLI，两者调用相同应用服务。

首版必须具备：

1. 浏览游戏版本，创建原版与 Fabric 实例，保存明确的游戏和加载器版本。
2. 微软 Device Code 登录、账户选择、令牌刷新、退出登录与错误说明；启动失败时不得回退到免认证账户。
3. 实例存档、模组、配置和日志隔离；全局设置允许实例覆盖。
4. Java 自动安装，以及手动指定 Java 可执行文件的能力。
5. 官方源与 BMCLAPI；支持来源优先级、严格指定来源、有限重试及失败回退。
6. 下载字节进度、校验、取消、中断恢复与安装状态管理。
7. 内存、JVM 参数、窗口设置，游戏日志、退出码及崩溃文件入口。
8. Windows 原生与 Linux 真实安装、启动验证。

后续阶段再加入 Forge、NeoForge、Quilt、Modrinth 搜索、模组依赖与 `.mrpack` 导入。CurseForge、旧版兼容、其他账户体系、ARM64、macOS、自动更新、终端图片与动画不属于首版承诺。

“支持所有历史版本”不作为首版目标。原先用于测试的离线登录已按用户最新要求移除；自有代码采用 MIT，Lighty 独立保留上游许可与版权声明。微软 API 接入与待验收事项记录于 [审核状态](app-review-status.md)。

## 3. 应用架构

初期采用两个 crate，以下目录已建立；当前仅包含基础模型、端口、配置服务与最小终端壳：

```text
crates/
  launcher-app/          实例、账户、Java、任务、来源策略、核心适配与进程服务
  launcher-terminal/     Ratatui TUI、Clap CLI、输入与展示
docs/                   规划、验证记录、接口决定
```

调用方向：

```text
TUI / CLI
    ↓ 命令与事件
应用服务：实例、账户、任务、Java、游戏生命周期
    ↓
Lighty 适配层 ← 来源策略与下载网络上下文
    ↓
Lighty：元数据、加载器、安装、参数生成及可复用执行能力
```

UI 只使用本项目的实例、任务、进度和错误类型，不保存 Lighty 构造器或令牌。适配层负责转换类型并屏蔽上游变化。

### 3.1 任务与事件

- 每项操作具有 TaskId，并关联稳定的 InstanceId；不使用显示名称作为唯一标识。
- 任务状态：排队、执行中、正在取消、成功、失败、已取消。
- 实例安装状态与游戏运行状态分开。安装未完成时不可显示为可启动。
- 执行任务持有子任务与取消令牌；取消时等待必要清理，不能只停止 UI 等待。
- 应用服务保存权威状态快照，事件用于通知更新。不能只靠广播事件累计状态，防止订阅过晚或事件丢失导致进度错误。
- 下载进度限频合并；终态事件可靠传递，UI 按状态变化和必要动画重绘。
- 错误保留阶段、资源、来源、是否可重试及底层原因；用户可查看详情。

## 4. Lighty 集成与上游补丁

优先扩展可注入接口并提交上游；上游尚未合入时使用固定提交的小型 fork。fork 只保留通用接口与修复，不把本项目的 BMCLAPI 策略硬编码进库中。

| 扩展点       | 预期边界                                 |
| --------- | ------------------------------------ |
| 下载网络上下文   | 所有下载类元数据、文件请求可通过统一接口；策略由应用注入         |
| Java 选择   | 支持托管 Java 或明确的可执行文件路径，并一致用于游戏和加载器处理器 |
| 取消        | 覆盖下载、安装、Java 安装和加载器处理器；清理边界明确        |
| 启动描述/执行控制 | 允许检查参数、环境和工作目录，接管或可靠控制进程             |
| 目录隔离      | 支持项目数据根目录及测试临时目录，避免不可控的全局状态          |

接口定义应位于 Lighty 可依赖的基础模块，应用实现来源策略；不能让 Lighty 反向依赖 launcher-app。原有用户不注入上下文时保持默认行为。

Lighty 的进程级 AppState、下载配置和实例管理器需要专项验证。若只能初始化一次，首版可在应用启动时配置，但运行期切换来源不得依赖修改共享全局变量；测试必要时使用独立进程隔离。

若扩展无法保持小范围，不自动改换已确认核心；先记录影响、替代接入方式与维护成本，再讨论范围。

## 5. 镜像下载源设计

### 5.1 基本原则

资源身份、原始地址与实际下载地址分离。镜像只改变请求位置，不改变文件身份、安装目标及预期校验值。源的选择必须发生在请求前，不能通过修改 hosts、全局代理或 HTTPS 中间人实现。

拟定接口职责：

| 类型/服务            | 职责                            |
| ---------------- | ----------------------------- |
| ResourceRequest  | 资源类别、逻辑标识、原始 URL、预期哈希及可用的大小信息 |
| MirrorProvider   | 判断是否支持该资源，生成候选地址；不支持时返回 None  |
| SourceRouter     | 按配置生成有序候选来源，不发起请求             |
| DownloadExecutor | 重试、续传、校验、文件提交、来源回退与进度         |
| MetadataService  | 元数据获取、缓存、解析及必要的镜像兼容处理         |

主流程：

```text
获取元数据 → 解析资源请求 → 生成有序候选来源
    → 下载到临时文件 → 校验 → 提交文件 → 更新安装状态
                         ↓ 失败
                   有限重试或切换来源
```

### 5.2 资源覆盖范围

| 资源类别                    | 首版处理                     |
| ----------------------- | ------------------------ |
| 版本清单、版本 JSON            | 官方与 BMCLAPI；版本查询也必须可使用镜像 |
| 资产索引、资源对象               | 索引及后续对象请求均经过路由           |
| 客户端 JAR、日志配置、依赖和原生库 JAR | 已知官方来源映射，保留预期哈希          |
| Fabric 元数据与 Maven 依赖    | API 与 Maven 分别适配         |
| Forge/NeoForge/Quilt    | 加入加载器支持时补齐来源适配和内部请求验证    |
| Java 元数据与压缩包            | 独立来源能力表；未验证的镜像路径不承诺支持    |
| Modrinth/CurseForge 内容  | 后续按各平台实际接口与文件来源接入，不泛化替换  |
| 登录与账户 API               | 认证专用客户端，禁止进入下载镜像路由       |

BMCLAPI 对资产、Maven 和 Fabric 元数据使用不同路径，例如 `/assets`、`/maven`、`/fabric-meta`。按文档与真实接口测试映射，不仅替换域名。

URL 处理使用解析库，精确匹配协议、主机与路径，保留必要的查询参数和编码。未知主机不擅自改写；BMCLAPI 兼容服务可配置基地址，其他协议通过新增 Provider 接入。

### 5.3 元数据与缓存

- 元数据中引用的文件 URL 解析后继续经过路由器，不能只代理第一层清单。
- 保留原始响应与来源记录，避免直接重写并覆盖官方版本 JSON。
- 有预期哈希的原始 JSON 先校验；镜像返回重写后的 JSON 时，走明确的兼容适配，不假定字节与官方一致，也不静默忽略哈希错误。
- 镜像响应若只保留镜像 URL，应通过资源逻辑标识与 Provider 规则建立候选来源；不能猜测任意 URL 的官方地址。
- 元数据缓存记录来源、抓取时间、TTL，以及可用的 ETag/Last-Modified；解析模型可按 schema 版本失效。
- 文件缓存尽量按内容哈希或标准资源路径复用，切换下载源无需全部重下。

### 5.4 可靠下载与回退

1. 在最终目标同目录创建专用临时文件，记录资源身份和来源；已校验完成的文件直接复用。
2. 同一来源失败时进行有限退避重试；区分网络失败、限流、文件缺失、服务错误和校验错误。
3. 处理 429 的 Retry-After 和主机冷却，限制每主机并发；总任务数和并发上限可配置。
4. 同源续传检查 Range 响应与文件身份；206 验证 Content-Range，200 按完整文件重写，416 触发检查或重新下载。
5. 首版切换来源时丢弃旧临时文件并重新下载，暂不做跨源续传。
6. 哈希与可用的大小信息通过后，以适合平台的方式提交文件；完成前不能标记资源可用。
7. 全部来源失败时保留明确错误及恢复入口。取消释放锁与任务资源，临时文件仅在身份可确认时用于下次恢复。
8. 没有可信哈希的文件采用明确的完整传输与大小检查策略；不把“文件存在”当作已验证。

下载应处理镜像的正常重定向；跨主机重定向不能携带不适用的认证信息。镜像下载不带微软账户令牌。

### 5.5 配置与界面

提供官方优先、镜像优先、仅指定来源三种模式；“仅指定来源”不会静默回退。默认使用官方还是 BMCLAPI 在首版发布前确定，不按用户地区暗中切换。

拟定配置示例（不是 Lighty 现有接口）：

```toml
[downloads]
sources = ["bmclapi", "official"]
max_concurrent_per_host = 8
retries_per_source = 2

[mirrors.bmclapi]
base_url = "https://bmclapi2.bangbang93.com"
```

该数值仅为项目拟定默认值，须结合服务要求和测试调整。来源策略支持按资源类别覆盖；同一任务使用一致的策略快照，新设置应用于后续任务。

TUI 显示当前资源来源、下载进度、回退原因，并按 BMCLAPI 文档要求标明来源。设置页允许检查地址和切换策略，诊断日志记录来源与响应状态但不泄露凭据。

## 6. 实例、Java 与账户

### 6.1 实例与存储

实例使用稳定 ID，显示名可修改，配置记录游戏版本、加载器与版本、Java 策略、内存、JVM 参数、窗口设置、首选账户和最近运行信息。持久化账户引用，不保存临时令牌。

逻辑存储布局：

```text
config/                    全局设置、账户资料与配置迁移信息
instances/<id>/            实例配置、安装状态
instances/<id>/minecraft/  saves、mods、config、options 等
cache/                     可恢复下载、元数据和可复用文件
runtimes/                  受管 Java，按系统与架构区分
logs/                      启动器与每次游戏运行日志
```

具体 OS 路径遵循 Windows 应用数据目录和 Linux XDG 规范，并允许明确的数据根目录覆盖。Lighty 目录通过适配层映射，不假定上游默认布局已实现共享缓存。

Windows 与 Linux 的运行时、原生库提取目录和安装状态隔离。初期不承诺跨系统共用同一个可变实例目录；跨平台共享文件缓存仅在哈希与平台归属可确认后引入。

安装与启动持有实例锁，防止两个启动器进程同时修改同一实例。配置保存采用原子写；删除实例前检查运行状态。

### 6.2 Java

- 支持自动选择和明确指定可执行文件，实例配置优先于全局默认。
- 实际运行 Java 探测版本与架构，而不是只检查路径存在。
- 结合游戏元数据与加载器要求选择 Java，不把某个版本永久写死为“最新 Java”。
- 安装处理器和游戏可有不同的运行时约束，分别解析需求并记录所选路径。
- 托管 Java 下载、校验、解压、权限和进度纳入同一任务体系；其镜像覆盖范围独立验证。
- 中文、空格和相对路径明确处理，最终启动使用结构化参数，不拼接 shell 命令。

### 6.3 账户与凭据

当前仅支持微软账户。原先用于测试的离线账户创建、UUID 生成及免认证启动路径已移除；旧记录不会进入可选账户列表。启动必须提供微软账户，经过在线认证和玩家资料获取，失败即停止。用户已注册 Client ID，恢复 Windows 微软登录联调，以下认证要求仍需真实验收。

微软采用 Device Code，显示网址与验证码，支持超时、取消和刷新。使用本项目注册的应用 Client ID，不需要重定向 URL；应用启用公共客户端流并允许个人微软账户。技术验证阶段确认 Minecraft Services 接入及账户资料获取，具体配置见 [微软登录说明](microsoft-login.zh-CN.md)。

账户资料和凭据分离；刷新令牌通过系统凭据服务保存，刷新轮换后及时更新。退出登录清理本地凭据，日志统一脱敏。

Linux/WSL 缺少可用 Secret Service 时支持仅本次会话保存，不静默降级为明文文件。不得直接 Debug 打印含令牌的上游对象或完整敏感启动参数。

## 7. 终端交互与进程生命周期

主界面为实例列表、选中实例详情和底部任务状态；账户、任务、日志、设置作为独立页面。界面支持窄窗口、中文与终端缩放。

当前确认的核心交互模型：

| 操作 | 按键 |
| --- | --- |
| 向上导航 | W / ↑ |
| 向下导航 | S / ↓ |
| 向左导航 | A / ← |
| 向右导航 | D / → |
| 确认 | Enter / 空格 |
| 返回 | Esc |

WASD 与对应方向键执行等效导航操作，Enter 与空格执行等效确认操作。其他交互暂不定义；具体页面的焦点规则、文字输入处理及额外快捷键留待后续设计。

UI 线程不执行网络、文件校验或等待游戏退出。启动、取消、重试和来源切换的进度与错误通过应用事件展示。

游戏 stdout/stderr 与启动器日志分流，日志落盘后可在 TUI 检索。启动流程记录实际 Java、版本、来源摘要和退出码，敏感字段脱敏。

关闭启动器与终止游戏是不同操作：运行游戏时普通退出应允许游戏继续运行；显式终止才结束游戏进程。技术验证必须检查 Lighty 日志后台任务和管道对该行为的影响，必要时调整日志文件连接与进程所有权。后台处理器则属于安装任务，取消安装时必须清理。

Windows 与 Unix 的终止行为分别实现并测试；发送终止信号不等于进程已退出。TUI 异常、错误返回和 Ctrl+C 路径均须恢复终端状态。

## 8. 平台与验证矩阵

| 环境               | 验证重点                                            |
| ---------------- | ----------------------------------------------- |
| Windows 原生       | Windows Terminal、中文/空格路径、账户凭据、Java、安装与真实启动、游戏退出 |
| WSL2（暂缓）       | 从本次范围调整起停止新增验收，保留既有构建与测试证据                    |
| WSLg（暂缓）       | 停止新增图形验收，保留已有 Linux 原版 / Fabric 主菜单证据             |
| Windows/Linux CI | fmt、Clippy、单元/集成测试、构建产物；核心配置与故障行为               |
| 原生 Linux 桌面      | 发布前补充图形、浏览器登录、凭据与进程生命周期验证                       |

规划阶段调用 WSL 列表曾返回 E_ACCESSDENIED；P0 后续已在具备执行权限的环境确认 FedoraLinux-44 / WSL2 与 WSLg。实际结果见 P0 记录，不把最初的权限错误当作 WSL 不可用。

采用固定版本作为回归样本，例如原版 1.20.1、1.21.1，以及明确版本的 Fabric；运行时要求从元数据解析。额外选择一个当时最新稳定版作冒烟，不能用动态 latest 取代可复现测试。

重点测试：

- 官方资源端点不可达、镜像可用时，完成版本查询、原版及 Fabric 安装启动。
- 镜像缺失、过期、限流、返回错误内容时，按配置回退；严格模式无隐式回退。
- 覆盖 302、200/206/416、续传、重试和切源，损坏文件不能变成正式缓存。
- 取消后无遗留安装处理器、不可启动的半完成实例有明确恢复入口。
- 错误 Java、架构不匹配、中文路径、两个同版本实例、重复启动和跨进程锁。
- 登录刷新、令牌轮换、退出清理及无系统凭据服务的会话模式。
- 终端渲染用状态/快照测试，覆盖窄窗口、弹窗和失败状态。

多数故障测试用本地模拟 HTTP 服务；外网接口测试单独执行；真实游戏窗口与账户流程人工验证。检查源码、构造启动命令、构建成功、真实进入游戏主菜单分别记录，不相互替代。

## 9. 分阶段交付与验收

### P0：Lighty 技术验证与补丁边界

交付：固定依赖记录、最小 CLI 验证入口、补丁清单、Windows 验证报告与已有 WSL 历史记录；新增 WSL / WSLg 验收暂缓。

验收：

- 工具链与发布包可用，记录源码与发布包差异。
- 当前要求原版、Fabric 在 Windows 完成安装并真实启动；WSL / WSLg 暂不作为当前 P0 验收门槛，恢复后单独复验。
- 手动 Java、微软账户、数据目录覆盖形成可验证路径；用户已提供 Client ID，Device Code 与刷新令牌保存继续 Windows 联调，真实游戏启动须在 API 接入后重新验收。
- 镜像覆盖元数据及文件请求；官方不可达场景通过，无遗漏的必要官方下载请求。
- 确认取消、游戏退出、关闭启动器后游戏继续运行的实现边界。

P0 是实现门槛，失败则先修复或明确范围，不提前堆叠 UI 功能。

### P1：应用服务与 CLI 闭环

交付：实例配置、账户、Java、可靠下载、镜像路由、安装/运行状态、日志与基础 CLI。

验收：无 TUI 也能完成登录、创建、安装、启动、查看日志及恢复失败任务；首版硬性要求有自动测试或人工证据。

### P2：TUI 首版

交付：实例、账户、任务、设置、日志页面及创建实例流程。

验收：核心流程支持 WASD / 方向键等效导航、Enter / 空格确认、Esc 返回；下载与游戏日志不阻塞输入；失败与取消状态清晰；窄窗口和异常退出恢复通过。

### P3：可靠性与双平台发布

交付：CI、故障回归、原生 Linux 桌面验证、Windows ZIP 与 Linux tar.gz、使用说明。

验收：发布产物在干净用户目录完成安装启动；镜像、路径、凭据、并发锁和进程行为通过验证，记录仍存在的限制。

### P4：加载器与内容扩展

顺序建议：NeoForge/Forge、Quilt、Modrinth 与 `.mrpack`，再评估 CurseForge。每次新增加载器须同时验证其元数据、依赖、处理器、Java 及镜像覆盖，不能仅增加 UI 选项。
